## Acceptance criteria

1. The entire plan is implemented on a single new branch created from main; main is untouched until final merge-back. The one exception is the workflow rename, done once on main after the merge (step 6).
2. A release tag is an upstream `v*` tag reachable from upstream main, betas included. Every other upstream `v*` tag (on a side branch such as `release/*`) is a hotfix tag. A tag that already has a rebrand commit is never synced again.
3. upstream-rebrand is never reset. The script's first run syncs every release tag after `v0.10.0-beta.1`, the newest tag it contains, and creates a hotfix branch for every hotfix tag whose base tag has a rebrand commit (today `v0.10.1`, then `v0.10.2`).
4. Each run syncs every release tag newer than the newest one on upstream-rebrand, and creates a branch for every hotfix tag that has none and whose base tag has a rebrand commit. Release tags go oldest first; a base tag is always handled before the hotfix tags built on it. A release tag must have a higher version number and a later tag date (when upstream added the tag; for a tag that records no date of its own, the date of the commit it points to) than the newest tag on upstream-rebrand. Among tags sharing a major.minor version (like `v0.10.0`, `v0.10.1`, `v0.10.2`), a higher version number must have a later tag date; hotfix tags are not compared across major.minor versions. Only tags with a higher version number than `v0.10.0-beta.1` are checked. A tag that breaks either rule fails the run with an error naming both tags, versions and dates. In every run, upstream-rebrand is synced before any hotfix branch. It never syncs an untagged upstream commit and never skips a release tag.
5. Each synced tag adds 2 commits: its **ours-merge commit**, a `-s ours` merge of the upstream tag; then its **rebrand commit**, the tag's tree minus the delete list, renamed and formatted by `fork/sync-upstream.sh`. "The rebrand commit for tag X" always means that second commit, on whichever branch synced X. A run knows X has a rebrand commit on a branch from git history alone, never from commit messages: the branch's first-parent history holds an ours-merge commit whose second parent is X's commit, and the rebrand commit is the next commit on that first-parent history. Provenance (criterion 18) reads the same links back. The **newest tag on upstream-rebrand** is the highest-versioned tag with a rebrand commit there, or `v0.10.0-beta.1` while none has one. Tags merely reachable from upstream-rebrand's older, unrebranded history do not count, so old hotfix tags such as `v0.7.1` get no branch.
6. A hotfix tag's **base tag** is the nearest tag it was built on in upstream history. The script creates each hotfix branch from the rebrand commit for its base tag: on upstream-rebrand when the base tag is a release tag, or on the base tag's own hotfix branch when it is a hotfix tag. A hotfix branch never moves after it is created.
7. For each hotfix tag, `git merge-base` of its rebrand commit and the rebrand commit for its base tag is the rebrand commit for its base tag.
8. Merging a hotfix tag's rebrand commit into a branch cut from the rebrand commit for its base tag brings only the changes between the base tag and the hotfix tag.
9. No upstream-rebrand or hotfix branch holds anything on the delete list (enumerated in the plan body: logo paths, `nix/npm-deps.hash`). Nothing from our main is ever copied into upstream-rebrand or any hotfix branch.
10. After the rebrand rename, no "paseo" in any case remains outside the rebrand skip paths ([rebrand.sh:33](../fork/rebrand.sh#L33): `PASEO-*`, `fork/`, `.github/workflows/merge-upstream.yml` (`sync-upstream.yml` after step 6), `*.paseo.ts`, `*.paseo.test.ts`).
11. The **target branch** is the branch the workflow or recipe was started on (normally main). The **merge branch** is `merge-<tag>`, named after the newest release tag on upstream-rebrand (like `merge-v0.11.0-beta.1`), cut from the target branch's tip; one per run. The merge into the merge branch keeps the target branch's copies of the files on the delete list.
12. The script takes no arguments. When upstream-rebrand holds every release tag, every hotfix tag eligible under criterion 4 has its branch, and the target branch contains upstream-rebrand, a run changes no branch on origin, creates no merge branch, and exits 0; local copies only move to match origin (criterion 17).
13. On a conflict merging upstream-rebrand into the merge branch, or a failing local check (criterion 22), upstream-rebrand and the new hotfix branches are still pushed, the merge branch is deleted and never pushed, the target branch on origin is unchanged, and the script exits non-zero listing the conflicted paths or the failing check. On any other error before upstream-rebrand and the hotfix branches are pushed, no branch on origin changes. On any other error after that push and before the merge branch is pushed, only upstream-rebrand and the new hotfix branches on origin have changed. In every case, local copies only move to match origin (criterion 17). Either way the script exits non-zero. No temporary worktree is left.
14. `just sync-upstream` and the sync workflow (`merge-upstream.yml` until step 6 renames it `sync-upstream.yml`) run the script, which does the whole run. It pushes upstream-rebrand, new hotfix branches and the merge branch; upstream-rebrand is never merged straight into the target branch. If the merge branch already exists on origin (made and fixed by hand after a stop), the script does not make a new one; it uses that branch. If a `merge-` branch for an older tag exists on origin, upstream-rebrand and hotfix branches still sync and push as normal, but the merge step is skipped and the script exits non-zero with an error naming that branch and saying it must land or be deleted first. It then waits for `ci.yml` on the merge branch. When every `ci.yml` job passes, it fast-forwards the target branch on origin to the merge branch with a push without force, and deletes the merge branch; the local target branch is not touched and catches up at the next run (criterion 17). It never makes a merge commit on the target branch. If the target branch moved so a fast-forward is impossible, the script exits non-zero naming both tips and leaves the merge branch; the user merges the target branch into it by hand, resolving any conflicts, and pushes it, and a re-run uses that branch. The 4 Playwright jobs (ids `playwright-1` to `playwright-4`, shown by GitHub as "playwright (shard N/4)") are ignored while `IGNORE_PLAYWRIGHT_TESTS` is on; it is an environment variable, on unless set to `0` or `false`, with a note beside its default saying to turn it off once the flaky Playwright tests are fixed. When any other job fails, or merging into the target branch fails, the script exits non-zero naming the failed job or conflict and leaves the merge branch and the target branch as they are. No ImageMagick or librsvg. After step 6, no old script, recipe, workflow or skill name remains in any tracked file outside `plans/`: `fork/sync-upstream-rebrand.sh`, `fork/merge-upstream.sh`, recipes `merge-upstream`, `sync-upstream-rebrand`, `trial-merge`, `merge-upstream.yml`, skill `merge`, `MERGE-SKILL.md`, `.trial-merge/`.
15. Every criterion in this section has an automated test, and the tests run in CI. A criterion that cannot be automated is not silently exempted: it is decomposed into testable parts, and any remainder is negotiated with the user before implementation.
16. A run of the sync workflow dispatched on the feature branch (`gh workflow run merge-upstream.yml --ref fix/upstream-sync`) completes green (`gh run view` reports success), treating `fix/upstream-sync` as the target branch: any merge branch is cut from and lands into `fix/upstream-sync`, never main. The workflow never hardcodes main.
17. Every run, on GitHub or locally, first fetches from origin upstream-rebrand, the target branch, the list of hotfix branches, and the hotfix branch any new hotfix is built on; if the fetch fails, the run fails. Origin's copy of upstream-rebrand and the hotfix branches wins: the local copies are set to match origin, dropping any local-only commits, and after the run's push they match origin again. The local target branch fast-forwards to origin's tip; if it has uncommitted changes or commits origin lacks, the run stops with a message naming them and changes nothing. No run builds on a stale local copy; a tag whose rebrand commit is already on origin is skipped. Pushes never force. upstream-rebrand and the new hotfix branches go in 1 atomic push: if any of them changed on origin during the run, that push fails and none of them change.
18. `just provenance` and the plan skill's Provenance section name the rebrand commit main last merged and the upstream tag it was built from, found through criterion 5's git links (the rebrand commit's parent is the ours-merge commit, whose second parent is the tag's commit), never from commit messages; the Provenance bullet labels (`main:`, `upstream-rebrand:`, `upstream/main:`) stay as `fork/check-plan.mjs` expects.
19. No hotfix branch is ever merged into main or any target branch by the script, a recipe or a workflow.
20. The script, recipes and workflows never hide, redirect to `/dev/null`, swallow or rewrite any command's output, errors or warnings; the script's own messages add to that output, never replace it. Git debug and trace modes stay off.
21. CI does not run on pushes to upstream-rebrand or `upstream-hotfix/*`. Those branches carry upstream's own `ci.yml`, which runs on pushes to main only (`git show upstream-rebrand:.github/workflows/ci.yml`, lines 3-5); a test asserts every rebrand commit's `ci.yml` keeps that main-only push trigger.
22. `RUN_LOCAL_CHECKS` is an environment variable, off when set to `0` or `false`: on in `just sync-upstream`, off in the sync workflow, because CI runs the same checks. When on, after a clean merge and before pushing the merge branch, the script runs `npm ci`, `npm run build:server`, then `npm run typecheck` and these unit tests in the temporary worktree: server and cli `test:unit`; desktop, client, highlight, plugin, protocol and relay `test`; app `vitest run --project unit`; each skips every test file whose name contains `e2e` or `integration`. No end-to-end, integration, browser or Playwright test runs locally. The first run (step 4) is `just sync-upstream` on `fix/upstream-sync`, and its type check and unit tests are green.

## Cause

The sync skips tags upstream main lacks ([sync-upstream-rebrand.sh:140](../fork/sync-upstream-rebrand.sh#L140)); release mode picks the newest tag of all ([merge-upstream.sh:60](../fork/merge-upstream.sh#L60)), today hotfix v0.10.2, then exits 1 because it is not on upstream main ([merge-upstream.sh:70](../fork/merge-upstream.sh#L70)). v0.10.1 and v0.10.2 are only on upstream's release branches. The sync copies main's nix hash into upstream-rebrand ([sync-upstream-rebrand.sh:109](../fork/sync-upstream-rebrand.sh#L109)) and needs ImageMagick or librsvg ([generate.mjs:34](../fork/brand/generate.mjs#L34)), absent in CI: the 2026-09-29 `merge-upstream.yml` run failed with "rsvg-convert is required".

## Constraints

- Delete-list entries are git pathspec globs matching both upstream's names and ours, in 1 block at the top of the script.
- All git work happens in temporary worktrees, with `LEFTHOOK=0`, except the fast-forward of the local target branch (criterion 17), done in place in the user's checkout. Refs move only after every commit exists.
- Upstream tags are read without adding them to our local tags, as the old sync does ([sync-upstream-rebrand.sh:38](../fork/sync-upstream-rebrand.sh#L38)).
- The tests follow `fork/build-changelog.test.mjs` (`node:test`).
