## Acceptance criteria

1. The entire plan is implemented on a single new branch created from main; main is untouched until main fast-forwards to the branch, with no merge commit on main. The one exception is the workflow rename, done once on main after the merge (step 7).
2. A release tag is an upstream `v*` tag reachable from upstream main, betas included. Every other upstream `v*` tag (on a side branch such as `release/*`, like `v0.10.1` and `v0.10.2`) is ignored: never synced, never given a branch, never checked, and no `upstream-hotfix/*` branch is ever created. A tag that already has a rebrand commit is never synced again.
3. upstream-rebrand is never reset. The script's first run syncs every release tag after `v0.10.0-beta.1`, the newest tag it contains.
4. Each run syncs every release tag newer than the newest one on upstream-rebrand, oldest first. A release tag must have a higher version number and a later tag date (when upstream added the tag; for a tag that records no date of its own, the date of the commit it points to) than the newest tag on upstream-rebrand. Among the release tags one run syncs, a higher version number must have a later tag date. A tag at or below `v0.10.0-beta.1` is skipped: never synced, never checked. A release tag at or below the newest tag on upstream-rebrand is skipped too, even when upstream adds it later. A tag that breaks either rule fails the run with an error naming both tags, versions and dates. It never syncs an untagged upstream commit and never skips a newer release tag.
5. Each synced tag adds 2 commits to upstream-rebrand: its **ours-merge commit**, a `-s ours` merge of the upstream tag; then its **rebrand commit**, the tag's tree minus the delete list, renamed and formatted by `fork/sync-upstream.sh`. "The rebrand commit for tag X" always means that second commit. A run knows X has a rebrand commit from git history alone, never from commit messages: upstream-rebrand's first-parent history holds an ours-merge commit whose second parent is X's commit, and the rebrand commit is the next commit on that first-parent history. Provenance (criterion 15) reads the same links back. The **newest tag on upstream-rebrand** is the highest-versioned tag with a rebrand commit there, or `v0.10.0-beta.1` while none has one. Tags merely reachable from upstream-rebrand's older, unrebranded history do not count.
6. No upstream-rebrand commit holds anything on the delete list (enumerated in the plan body: logo paths, `nix/npm-deps.hash`). Nothing from our main is ever copied into upstream-rebrand.
7. After the rebrand rename, no "paseo" in any case remains outside the rebrand skip paths ([rebrand.sh:33](../fork/rebrand.sh#L33): `PASEO-*`, `fork/`, `.github/workflows/sync-upstream.rambla.yml` (`sync-upstream.yml` after step 7), `*.paseo.ts`, `*.paseo.test.ts`).
8. The **target branch** is the branch the workflow or recipe was started on (normally main). The merge step handles each release tag whose rebrand commit the target branch lacks, one at a time, oldest first. Each tag's **merge branch** is `merge-<tag>` (like `merge-v0.11.0-beta.1`), cut from the target branch's tip, and merges only that tag's rebrand commit as a real merge commit, never squashed or rebased: its first parent is the target branch's tip and its second parent is the tag's rebrand commit, so the target branch's history traces every landed tag back to its upstream commit (merge commit, then rebrand commit, then ours-merge commit, whose second parent is the upstream tag's commit); it lands in the target branch before the next tag's merge branch is made. The first tag that stops (criteria 10 and 11) ends the run; tags before it stay landed. The merge into the merge branch keeps the target branch's copies of the files on the delete list.
9. The script takes no arguments. When upstream-rebrand holds every release tag and the target branch contains upstream-rebrand, a run changes no branch on origin, creates no merge branch, and exits 0; local copies only move to match origin (criterion 14).
10. On a conflict merging a tag's rebrand commit into its merge branch, upstream-rebrand is still pushed, that merge branch is deleted and never pushed, the target branch on origin gains nothing beyond the tags that already landed in this run, and the script exits non-zero listing the conflicted paths. On a failing local check (criterion 18), the merge branch is kept: it is pushed and left on origin for the user to fix, the target branch on origin gains nothing beyond the tags that already landed in this run, and the script exits non-zero naming the failing check; a re-run uses that branch (criterion 11). On any other error before upstream-rebrand is pushed, no branch on origin changes. On any other error after that push and before the merge branch is pushed, only upstream-rebrand on origin has changed. In every case, local copies only move to match origin (criterion 14). Either way the script exits non-zero. No temporary worktree is left.
11. `just sync-upstream` and the sync workflow (`sync-upstream.rambla.yml` until step 7 renames it `sync-upstream.yml`) run the script, which does the whole run. The sync workflow runs once a day on a schedule and can also be started by hand. It pushes upstream-rebrand and the merge branch; upstream-rebrand is never merged straight into the target branch. If the merge branch already exists on origin (made and fixed by hand after a stop), the script does not make a new one; it uses that branch. If a `merge-` branch for any other tag exists on origin, upstream-rebrand still syncs and pushes as normal, but the merge step is skipped and the script exits non-zero with an error naming that branch and saying it must land or be deleted first. It then waits for `ci.yml` on the merge branch. When every `ci.yml` job passes, it fast-forwards the target branch on origin to the merge branch with a push without force, and deletes the merge branch; the local target branch is not touched and catches up at the next run (criterion 14). It never makes a merge commit on the target branch. If the target branch moved so a fast-forward is impossible, the script exits non-zero naming both tips and leaves the merge branch; the user merges the target branch into it by hand, resolving any conflicts, and pushes it, and a re-run uses that branch. The 4 Playwright jobs (ids `playwright-1` to `playwright-4`, shown by GitHub as "playwright (shard N/4)") are ignored while `IGNORE_PLAYWRIGHT_TESTS` is on; it is an environment variable, on unless set to `0` or `false`, with a note beside its default saying to turn it off once the flaky Playwright tests are fixed. When any other job fails, or merging into the target branch fails, the script exits non-zero naming the failed job or conflict and leaves the merge branch and the target branch as they are. No ImageMagick or librsvg. After step 7, no old script, recipe, workflow or skill name remains in any tracked file outside `plans/`: `fork/sync-upstream-rebrand.sh`, `fork/merge-upstream.sh`, recipes `merge-upstream`, `sync-upstream-rebrand`, `trial-merge`, `sync-upstream.rambla.yml`, skill `merge`, `MERGE-SKILL.md`, `.trial-merge/`.
12. Every criterion in this section has an automated test, and the tests run in CI. A criterion that cannot be automated is not silently exempted: it is decomposed into testable parts, and any remainder is negotiated with the user before implementation.
13. A run of the sync workflow dispatched on the feature branch (`gh workflow run sync-upstream.rambla.yml --ref fix/upstream-sync`) completes green (`gh run view` reports success), treating `fix/upstream-sync` as the target branch: any merge branch is cut from and lands into `fix/upstream-sync`, never main. The workflow never hardcodes main.
14. Every run, on GitHub or locally, first fetches upstream-rebrand and the target branch from origin; if the fetch fails, the run fails. Origin's copy of upstream-rebrand wins: the local copy is set to match origin, dropping any local-only commits, and after the run's push it matches origin again. The local target branch fast-forwards to origin's tip; if it has uncommitted changes or commits origin lacks, the run stops with a message naming them and changes nothing. No run builds on a stale local copy; a tag whose rebrand commit is already on origin is skipped. Pushes never force: if upstream-rebrand changed on origin during the run, its push fails and it does not change.
15. `just provenance` and the plan skill's Provenance section name the rebrand commit main last merged and the upstream tag it was built from, found through criterion 5's git links (the rebrand commit's parent is the ours-merge commit, whose second parent is the tag's commit), never from commit messages; the Provenance bullet labels (`main:`, `upstream-rebrand:`, `upstream/main:`) stay as `fork/check-plan.mjs` expects.
16. The script, recipes and workflows never hide, redirect to `/dev/null`, swallow or rewrite any command's output, errors or warnings; the script's own messages add to that output, never replace it. Git debug and trace modes stay off.
17. CI does not run on pushes to upstream-rebrand. It carries upstream's own `ci.yml`, which runs on pushes to main only (`git show upstream-rebrand:.github/workflows/ci.yml`, lines 3-5); a test asserts every rebrand commit's `ci.yml` keeps that main-only push trigger.
18. `RUN_LOCAL_CHECKS` is an environment variable, off when set to `0` or `false`: on in `just sync-upstream`, off in the sync workflow, because CI runs the same checks. When on, after a clean merge and before pushing the merge branch, the script runs `npm ci`, `npm run build:server`, then `npm run typecheck` and these unit tests in the temporary worktree: server and cli `test:unit`; desktop, client, highlight, plugin, protocol and relay `test`; app `vitest run --project unit`; each skips every test file whose name contains `e2e` or `integration`. No end-to-end, integration, browser or Playwright test runs locally. The first run (step 4) is `just sync-upstream` on `fix/upstream-sync`, run by the user, and its local checks run.
